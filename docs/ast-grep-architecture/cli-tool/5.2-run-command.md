The `run` command provides ad-hoc pattern-based searching and rewriting of code without requiring rule configuration files. It is the primary command for one-time searches, quick code exploration, and interactive rewrites using AST pattern syntax.

For rule-based scanning with YAML configuration, see [Scan Command](/ast-grep/ast-grep/5.3-scan-command). For batch testing of rules, see [Testing Rules](/ast-grep/ast-grep/3.4-testing-rules).

---

## Purpose and Capabilities

The `run` command executes single pattern searches across a codebase by:

-   Parsing source files using tree-sitter
-   Matching an AST pattern against parsed trees
-   Optionally applying rewrites to matched code
-   Supporting both explicit language specification and automatic inference
-   Providing multiple output formats (colored terminal, JSON, file names only)

Unlike the `scan` command which processes multiple rules from configuration files, `run` accepts a single pattern as a command-line argument and is optimized for interactive use.

## Command-Line Arguments

The `RunArg` structure defines all configurable options for the run command:

| Argument Group | Key Options | Purpose |
| --- | --- | --- |
| **Pattern** | `--pattern, -p` | AST pattern to match (required) |
| | `--selector` | Extract sub-node kind from pattern |
| | `--rewrite, -r` | Template to replace matched nodes |
| **Language** | `--lang, -l` | Explicit language specification |
| | `--strictness` | Match strictness level (cst, smart, ast, relaxed, signature, template) |
| **Debugging** | `--debug-query` | Display pattern's tree-sitter AST |
| **Input** | `InputArgs` | Paths, stdin, globs, follow symlinks, threads |
| **Output** | `OutputArgs` | Color, interactive, JSON, update-all |
| **Context** | `ContextArgs` | Before/after context lines |
| **Display** | `--heading` | Control file name heading display |

### Pattern Options

The `selector` option enables matching a sub-part of the pattern. For example, with pattern `function $NAME() {}` and selector `identifier`, only the function name is matched.

### Strictness Levels

The `Strictness` enum wrapper around `MatchStrictness` defines six matching modes:

-   **cst**: Match all nodes exactly including trivia
-   **smart**: Match all nodes except source trivial nodes (default)
-   **ast**: Match only AST nodes
-   **relaxed**: Match AST nodes except comments
-   **signature**: Match AST structure without text content
-   **template**: Match text only, ignoring node kinds

## Execution Flow

The flow begins at `run_with_pattern()` which:

1.  Loads the optional `ProjectConfig` for custom language configurations
2.  Selects the appropriate `Printer` implementation based on output flags
3.  Dispatches to one of three worker strategies based on input mode and language specification
4.  Returns exit code 0 if matches found, 1 otherwise

**Sources:** [crates/cli/src/run.rs151-174](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/run.rs#L151-L174) [crates/cli/src/run.rs176-185](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/run.rs#L176-L185)

## Worker Implementations

The run command uses two worker implementations depending on whether the language is explicitly specified:

### RunWithSpecificLang

Used when `--lang` is provided or reading from stdin. This worker:

```rust
struct RunWithSpecificLang {
    args: RunArg,
    pattern: Pattern,
    lang: SgLang,
    // ...
}
```

Key characteristics:

-   Pattern compiled once during initialization
-   File walker filtered to only include files matching the specified language
-   Supports matching within injected languages (e.g., JavaScript in HTML)

**Sources:** [crates/cli/src/run.rs260-344](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/run.rs#L260-L344) [crates/cli/src/run.rs309-343](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/run.rs#L309-L343)

### RunWithInferredLang

Used when no `--lang` is specified. Language is inferred from file extensions:

```rust
struct RunWithInferredLang {
    args: RunArg,
    // Pattern built per file based on detected language
}
```

Key characteristics:

-   Pattern built per file based on detected language
-   Automatically handles injectable languages (e.g., CSS in Vue files)
-   `Fixer` built per match unit to handle different sub-languages
-   More flexible but potentially slower for large codebases

**Sources:** [crates/cli/src/run.rs187-258](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/run.rs#L187-L258) [crates/cli/src/run.rs210-257](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/run.rs#L210-L257)

## Pattern Matching Process

The core matching logic is encapsulated in `match_one_file()`:

```rust
fn match_one_file(
    &self,
    path: &Path,
    content: &str,
) -> Result<Vec<MatchUnit>> {
    // Parse file, apply pattern, return matches
}
```

The `MatchUnit` structure contains:

-   `path`: File path being processed
-   `grep`: Parsed AST root with source text
-   `matcher`: Compiled pattern or matcher

When a rewrite template is provided, `Diff::generate()` creates a diff object showing the before/after text transformation.

## Standard Input Processing

When `--stdin` is specified, `RunWithSpecificLang` implements the `StdInWorker` trait:

```rust
impl StdInWorker for RunWithSpecificLang {
    fn parse_stdin(&self, content: String) -> Result<Vec<MatchUnit>> {
        // Process stdin content with explicit language
    }
}
```

Standard input processing:

-   Requires explicit language specification (no inference possible)
-   Path is set to `"STDIN"` for display purposes
-   Single-threaded processing (no parallelism)

## Language Injection Support

Both worker implementations support language injection for multi-language files:

```rust
// Process both root and injected languages
for lang in injected_languages {
    let matches = match_with_injection(&lang, &content);
    // ...
}
```

This enables matching patterns in:

-   JavaScript within HTML `<script>` tags
-   CSS within Vue `<style>` sections
-   TypeScript within MDX files

The `filter_file_pattern()` utility function processes both root and injected language regions, returning `MatchUnit` objects for each applicable region.

## Output Processing

### Printer Selection

The command selects different printer implementations based on flags:

| Flag | Printer Type | Purpose |
| --- | --- | --- |
| `--files-with-matches` | `FileNamePrinter` | Output only file paths with matches |
| `--json` | `JSONPrinter` | Structured JSON output |
| `--interactive` | `InteractivePrinter` | Interactive accept/reject prompts |
| (default) | `ColoredPrinter` | Colored terminal output with context |

### Exit Code Behavior

The run command returns different exit codes based on results:

-   **Exit 0**: Matches found
-   **Exit 1**: No matches found (not an error)
-   **Exit with error**: Pattern parsing failed or has errors

This enables shell scripting workflows where exit code indicates whether a pattern exists in the codebase.

## Heading Display Control

The `--heading` option controls file name display format:

```rust
enum Heading {
    Auto,   // Use heading when outputting to terminal
    Always, // Always show file names as headings
    Never,  // Show file path as prefix before each match
}
```

Heading modes:

-   **auto** (default): Use heading when outputting to terminal, disable when piping
-   **always**: Always show file names as headings before matches
-   **never**: Show file path as prefix before each match

This affects the `ColoredPrinter` configuration, making output more readable for different use cases (interactive vs. scripted).

## Integration with Project Configuration

While the run command doesn't require `sgconfig.yml`, it optionally loads `ProjectConfig`:

```rust
let project = project.unwrap_or_default();
run_with_pattern(args, project)?;
```

The project configuration provides:

-   Custom language definitions via dynamic loading
-   Global settings that may affect parsing
-   Inspection/trace capabilities for debugging

The configuration is loaded at the CLI entry point in `lib.rs` and passed to all commands, allowing run to benefit from project-level language customizations even when not using rules.

**Sources:** [crates/cli/src/run.rs151-154](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/run.rs#L151-L154) [crates/cli/src/lib.rs102-123](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lib.rs#L102-L123)

## Common Usage Patterns

### Quick Search

```bash
sg run -p 'console.log($MSG)' -l js ./src
```

### Search with Rewrite Preview

```bash
sg run -p 'var $X = $Y' -r 'let $X = $Y' -l js ./src
```

### Interactive Rewrite

```bash
sg run -p 'var $X = $Y' -r 'let $X = $Y' -i ./src
```

### JSON Output for Tooling

```bash
sg run -p 'console.log($MSG)' -l js --json ./src
```

### Debug Pattern Parsing

```bash
sg run -p 'function $NAME() {}' -l js --debug-query
```

Each of these patterns leverages different combinations of the `RunArg` options to achieve specific workflows, from simple searching to interactive code transformation.
