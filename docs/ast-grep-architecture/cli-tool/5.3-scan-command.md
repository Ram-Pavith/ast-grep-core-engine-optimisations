The scan command performs rule-based code analysis across a codebase by applying a collection of predefined rules from configuration files. Unlike the run command which executes ad-hoc pattern searches (see [Run Command](/ast-grep/ast-grep/5.2-run-command)), the scan command is designed for systematic codebase auditing using rules defined in YAML files, typically as part of a project configuration.

The scan command outputs diagnostics with configurable severity levels (error, warning, hint, info), supports automatic fixes, and can generate reports in multiple formats including JSON, SARIF, and platform-specific formats for CI/CD integration.

## Command Arguments

The `ScanArg` struct defines all command-line options accepted by the scan command:

| Argument | Type | Purpose |
| --- | --- | --- |
| `--rule` / `-r` | `PathBuf` | Path to a single rule file for ad-hoc scanning without project setup |
| `--inline-rules` | `String` | Rule definitions as inline YAML text, separated by `---` for multiple rules |
| `--format` | `Platform` | Output format (GitHub Actions, SARIF) for CI/CD integration |
| `--report-style` | `ReportStyle` | Display style (rich or short), defaults to rich |
| `--include-metadata` | flag | Include rule metadata in JSON output (requires `--json`) |
| `--max-results` | `u16` | Stop scanning after reaching this number of results |
| Severity overwrites | `OverwriteArgs` | Filter rules by severity or override rule severities |
| Input args | `InputArgs` | File paths, globs, stdin mode, parallel threads |
| Output args | `OutputArgs` | JSON, interactive mode, color, file-name-only output |
| Context args | `ContextArgs` | Before/after context lines for matches |

The `--rule` and `--inline-rules` options are mutually exclusive. When neither is provided, the scan command loads rules from the project configuration specified by `sgconfig.yml`.

## Rule Loading Strategies

The scan command supports three distinct strategies for loading rules, evaluated in this order of precedence:

**Rule Loading Strategy Diagram**: The scan command prioritizes single-file rules (`--rule`), then inline rules (`--inline-rules`), and finally falls back to project configuration. For stdin mode, either `--rule` or `--inline-rules` is required.

### Single Rule File

When `--rule` is specified, the command reads rules from the specified YAML file using `read_rule_file()`. The project directory is set to the parent directory of the rule file:

```rust
let configs = read_rule_file(&self.rule)?;
let proj_dir = self.rule.parent().unwrap_or(Path::new("")).to_path_buf();
```

This mode is useful for testing individual rules without a full project setup.

Sources: [crates/cli/src/scan.rs144-147](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/scan.rs#L144-L147)

### Inline Rules

When `--inline-rules` is provided, the command parses rule definitions directly from the command-line argument string. Multiple rules can be specified by separating them with `---`:

```bash
sg scan --inline-rules '
id: no-console
language: js
rule:
  pattern: console.log($MSG)
message: Avoid console.log
'
```

Sources: [crates/cli/src/scan.rs148-151](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/scan.rs#L148-L151)

### Project Configuration

When neither single-file nor inline rules are specified, the scan command loads rules from the project configuration returned by `ProjectConfig::find_rules()`. This method applies `RuleOverwrite` settings to filter or modify rule severities based on command-line flags:

```rust
let configs = project.find_rules(&self.overwrite)?;
```

### CombinedScan Integration

For each file processed, `ScanWithConfig::produce_item()` applies all relevant rules using `CombinedScan`:

```rust
fn produce_item(&self, path: &Path) -> Option<Vec<ScanResult>> {
    let combined = CombinedScan::new(&self.configs);
    let results = combined.scan_file(&path, &content)?;
    // ... process results
}
```

The `separate_fix` parameter controls whether fixes are processed separately for interactive review or combined with diagnostic output.

### Result Limiting

When `--max-results` is specified, the worker uses `MaxItemCounter` to atomically claim slots across parallel workers and truncate results:

```rust
struct MaxItemCounter {
    count: AtomicUsize,
    limit: u16,
}
```

The `should_stop()` method checks whether the limit has been reached to terminate parallel processing early.

### ScanStdin

The `ScanStdin` worker handles stdin input, which requires either `--rule` or `--inline-rules` to be specified:

| Field | Type | Purpose |
| --- | --- | --- |
| `rules` | `Vec<RuleConfig<SgLang>>` | Rules to apply (must be specified via CLI) |
| `error_count` | `AtomicUsize` | Thread-safe error counter |

The `parse_stdin()` implementation assumes all rules target the same language (taken from `rules[0].language`) and creates a `CombinedScan` without separate fix processing:

```rust
    let lang = self.rules[0].language;

    // ... scan stdin content
}
```

## Unused Suppression Detection

The scan command includes a special built-in rule to detect unused suppression comments. This rule is automatically configured based on whether all project rules are being scanned:

**Unused Suppression Detection Logic**: The default severity is `Hint` when scanning all rules (to catch suppressions that don't match any active rules), but `Off` for partial scans (to avoid false positives when some rules aren't loaded).

The logic for determining default severity:

```rust
fn get_unused_suppression_severity(&self) -> Severity {
    if self.include_all_rules() {
        Severity::Hint  // All rules loaded, so unused suppressions are suspicious
    } else {
        Severity::Off   // Partial scan, suppressions might be for other rules
    }
}
```

Users can explicitly override this with `--error unused-suppression` or other severity flags through the `RuleOverwrite` mechanism.

## Error Handling and Exit Codes

The scan command tracks errors across parallel workers using `AtomicUsize`:

```rust
struct ScanWorker {
    error_count: Arc<AtomicUsize>,
}

// When a rule with severity: error matches
if diagnostic.severity == Severity::Error {
    self.error_count.fetch_add(1, Ordering::SeqCst);
}
```

After all items are consumed, the worker checks the accumulated error count and returns a failure exit code if any errors were found:

```rust
fn consume_items(&self, items: ...) -> Result<ExitCode> {
    // ... process all items
    if self.error_count.load(Ordering::SeqCst) > 0 {
        Err(anyhow!(EC::DiagnosticError(error_count)))
    } else {
        Ok(ExitCode::SUCCESS)
    }
}
```

This allows the scan command to fail CI/CD pipelines when rules with `severity: error` match.

## Comparison with Run Command

| Aspect | Scan Command | Run Command |
| --- | --- | --- |
| **Purpose** | Rule-based codebase analysis | Ad-hoc pattern search |
| **Rule Source** | `RuleCollection` from config/file | Single `Pattern` from CLI arg |
| **Severity Levels** | error, warning, hint, info, off | N/A (all matches equal) |
| **Auto-fixes** | Per-rule `fix` templates | Single `--rewrite` template |
| **Exit Code** | Fails if errors found | Fails if no matches (or pattern error) |
| **Metadata** | Rule ID, message, severity, docs | N/A |
| **Unused Suppression** | Detected automatically | N/A |
| **Multiple Languages** | Rules specify per-rule | Single `--lang` for all |

The scan command is designed for systematic code quality enforcement, while the run command is optimized for exploratory searches and quick rewrites.
