## Purpose and Scope

This document explains the architecture of the Language Server Protocol (LSP) implementation in ast-grep, which enables IDE integration for real-time diagnostics and code analysis. It covers the tower-lsp-based server setup, the rule_finder closure pattern for dynamic rule loading, and the asynchronous request handling model.

For information about IDE editor configuration and usage, see [Editor Integration](/ast-grep/ast-grep/6.2-editor-integration). For details about the rule system that the LSP server uses, see [Rule Configuration Format](/ast-grep/ast-grep/3.1-rule-configuration-format) and [Rule Components](/ast-grep/ast-grep/3.2-rule-components).

## Architecture Overview

The LSP implementation consists of two layers: the `ast-grep-lsp` crate provides the core language server implementation, while `ast-grep-cli` integrates it with the project configuration system. The `ast-grep-lsp` crate depends on `tower-lsp-server` for LSP protocol handling and uses a rule finder closure pattern for dynamic rule loading.

## Server Initialization

The LSP server initialization occurs in the CLI layer, which creates a tokio async runtime, validates the project configuration, constructs the rule finder closure, and launches the tower-lsp server.

**Initialization Sequence:**

```
┌──────────────────────────────────────────────────────────────────────┐
│                         Initialization Flow                          │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  main_with_args()                                                    │
│       │                                                              │
│       ▼                                                              │
│  Commands::Lsp(LspArg) ──────────────────────────────────────────┐  │
│       │                                                          │  │
│       ▼                                                          │  │
│  run_language_server()                                           │  │
│       │                                                          │  │
│       ├─► tokio::runtime::Builder::new_multi_thread()            │  │
│       │       .enable_all()                                       │  │
│       │       .build()?                                           │  │
│       │                                                          │  │
│       ▼                                                          │  │
│  runtime.block_on(run_language_server_impl())                    │  │
│       │                                                          │  │
│       ├─► project = ProjectConfig::setup()?                      │  │
│       │                                                          │  │
│       ├─► config_base = project.project_dir.clone()              │  │
│       │                                                          │  │
│       ├─► rule_finder = move || project.find_rules(...)          │  │
│       │                                                          │  │
│       ├─► (service, socket) = LspService::build(Backend::new)    │  │
│       │                                                          │  │
│       └─► Server::new(stdin, stdout, socket).serve(service)      │  │
│               .await                                             │  │
│                                                                  │  │
└──────────────────────────────────────────────────────────────────────┘
```

**Sources:** [crates/cli/src/lsp.rs10-37](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lsp.rs#L10-L37)

**Initialization Steps:**

| Step | Function | Purpose |
| --- | --- | --- |
| 1 | `tokio::runtime::Builder::new_multi_thread()` | Create work-stealing thread pool |
| 2 | `.enable_all()` | Enable I/O, time, and signal drivers |
| 3 | `.build()` | Construct runtime |
| 4 | `.block_on(run_language_server_impl)` | Execute async initialization |
| 5 | `project?` | Validate ProjectConfig exists |
| 6 | `config_base = project_dir.clone()` | Capture base directory path |
| 7 | `move \| \| { ... }` | Create rule_finder closure |
| 8 | `LspService::build(...)` | Construct service and socket |
| 9 | `Server::new(stdin, stdout, socket)` | Create server instance |
| 10 | `.serve(service).await` | Start LSP event loop |

The initialization fails early if `ProjectConfig::setup()` returns an error, which occurs when no `sgconfig.yml` or `sgconfig.yaml` file is found in the current directory or parent directories.

## Rule Finder Closure Pattern

The rule finder is a closure that decouples rule loading from the LSP backend implementation. This pattern allows the `ast-grep-lsp` crate to remain independent of the CLI configuration system while enabling dynamic rule discovery.

**Closure Type Signature and Lifetime:**

```rust
type RuleFinder = Box<dyn FnMut() -> Result<RuleCollection<SgLang>> + Send>;

// Created as:
let rule_finder = move || {
    project_config.find_rules(&RuleOverwrite::default())
};
```

**Sources:** [crates/cli/src/lsp.rs19-23](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lsp.rs#L19-L23) [crates/cli/src/config.rs85-91](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/config.rs#L85-L91)

**Closure Implementation:**

The rule finder is a move closure defined at [crates/cli/src/lsp.rs20-23](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lsp.rs#L20-L23):

```rust
let rule_finder = move || {
    let (rules, _trace) = project.find_rules(&RuleOverwrite::default())?;
    Ok(rules)
};
```

**Architectural Benefits:**

| Aspect | Implementation Detail |
| --- | --- |
| **Decoupling** | `ast-grep-lsp` crate has no dependency on `ProjectConfig` or `ast-grep-cli` types |
| **Ownership** | `move` keyword transfers `project_config` ownership to closure |
| **Error Propagation** | `Result` type allows Backend to handle rule loading failures gracefully |
| **Lazy Evaluation** | Rules loaded on-demand when Backend invokes closure |
| **Extension Point** | Closure signature enables future rule reloading without API changes |

**Rule Discovery Process:**

When the closure executes `project_config.find_rules(RuleOverwrite::default())`, it performs:

1.  **Utility Rule Loading** [crates/cli/src/config.rs133-162](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/config.rs#L133-L162): Walks `util_dirs`, parses YAML into `GlobalRules`
2.  **Main Rule Discovery** [crates/cli/src/config.rs164-219](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/config.rs#L164-L219): Walks `rule_dirs`, reads rule files, validates meta-variables
3.  **Rule Collection Construction** [crates/cli/src/config.rs212](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/config.rs#L212-L212): Creates `RuleCollection::try_new(configs)` with glob pattern support
4.  **Trace Generation**: Returns `RuleTrace` (discarded by LSP) containing effective and skipped rule counts

**Sources:** [crates/cli/src/lsp.rs19-23](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lsp.rs#L19-L23) [crates/cli/src/config.rs85-91](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/config.rs#L85-L91) [crates/cli/src/config.rs133-162](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/config.rs#L133-L162) [crates/cli/src/config.rs164-219](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/config.rs#L164-L219)

## Async Communication Model

The LSP server runs on a tokio multi-threaded async runtime, using `tower-lsp-server` for JSON-RPC protocol handling over stdin/stdout. The `Backend` struct in `ast-grep-lsp` implements LSP request handlers that are invoked asynchronously by the `LspService`.

**Message Processing Architecture:**

```
┌─────────────────────────────────────────────────────────────────────┐
│                      Async Message Processing                       │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│    stdin (non-blocking)                                            │
│         │                                                           │
│         ▼                                                           │
│    ┌─────────────────────────────────────┐                         │
│    │           Server                     │                         │
│    │  (JSON-RPC message reading)          │                         │
│    └──────────────────┬──────────────────┘                         │
│                       │                                             │
│                       ▼                                             │
│    ┌─────────────────────────────────────┐                         │
│    │          LspService                  │                         │
│    │  (async request dispatch)            │                         │
│    │                                      │                         │
│    │  ┌────────────────────────────────┐ │                         │
│    │  │   Handler Method Selection     │ │                         │
│    │  │   (based on LSP method name)   │ │                         │
│    │  └────────────────┬───────────────┘ │                         │
│    └───────────────────┼─────────────────┘                         │
│                        │                                            │
│                        ▼                                            │
│    ┌─────────────────────────────────────┐                         │
│    │            Backend                   │                         │
│    │  (async handler implementation)      │                         │
│    │                                      │                         │
│    │  • initialize()                      │                         │
│    │  • did_open()                        │                         │

│                       │                                             │
│                       ▼                                             │
│    stdout (non-blocking) ◄── JSON-RPC response                     │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Sources:** [crates/cli/src/lsp.rs14-28](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lsp.rs#L14-L28) [crates/lsp/Cargo.toml26](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/lsp/Cargo.toml#L26-L26)

**Tokio Runtime Configuration:**

[crates/cli/src/lsp.rs32-36](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lsp.rs#L32-L36) configures the runtime:

| Configuration | Purpose |
| --- | --- |
| `new_multi_thread()` | Creates work-stealing thread pool (sized to available CPU cores) |
| `enable_all()` | Enables time driver, I/O driver, and signal handling |
| `build()` | Constructs the `Runtime` instance |
| `block_on(async_fn)` | Blocks main thread, executes async LSP server until shutdown |

**LspService Construction:**

The service is built using a factory closure pattern at [crates/cli/src/lsp.rs25-26](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lsp.rs#L25-L26):

```rust
let (service, socket) = LspService::build(|client| {
    Backend::new(client, config_base, rule_finder)
}).finish();
```

**Construction Process:**

1.  `LspService::build()` accepts a factory closure `|client| -> Backend`
2.  The factory receives a `Client` handle for sending notifications/requests to the IDE
3.  `Backend::new(client, config_base, rule_finder)` constructs the Backend instance
4.  `.finish()` returns `(service, socket)` tuple
5.  `service` implements LSP request handlers
6.  `socket` is the message channel between Server and Service

**Server Event Loop:**

`Server::new(stdin, stdout, socket).serve(service).await` at [crates/cli/src/lsp.rs27](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lsp.rs#L27-L27) establishes the event loop:

-   Continuously reads JSON-RPC messages from stdin (non-blocking)
-   Deserializes messages and routes to appropriate LspService handler
-   Serializes responses and writes to stdout (non-blocking)
-   Runs until IDE sends `shutdown` request followed by `exit` notification

**Sources:** [crates/cli/src/lsp.rs25-28](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lsp.rs#L25-L28)

## Project Configuration Integration

The LSP server depends on `ProjectConfig` to discover `sgconfig.yml`, load utility rules, and collect main rules. The configuration discovery occurs during CLI initialization before the Backend is constructed.

**ProjectConfig Structure:**

| --- | --- | --- |
| `project_dir` | `PathBuf` | Base directory containing sgconfig.yml (used by Backend for path resolution) |
| `rule_dirs` | `Vec<PathBuf>` | Directories to scan for rule YAML files (relative to project_dir) |
| `test_configs` | `Option<Vec<TestConfig>>` | Test directories (unused by LSP, used by `sg test` command) |
| `util_dirs` | `Option<Vec<PathBuf>>` | Directories containing global utility rules |

**Configuration File Discovery:**

1.  `sgconfig.yml` in current directory
2.  `sgconfig.yaml` in current directory (if .yml not found)
3.  Recursively walks up parent directories repeating steps 1-2
4.  Returns `None` if filesystem root reached without finding config

## Error Handling

The LSP implementation uses a layered error handling strategy that distinguishes between fatal initialization errors and recoverable runtime errors.

**Error Categories:**

| Error Type | Location | Behavior | Example |
| --- | --- | --- | --- |
| **Initialization Errors** | `run_language_server()` | Fatal, exits before server starts | No sgconfig.yml found |
| **Runtime Errors** | Tokio runtime creation | Fatal, cannot serve requests | `.build()` fails |
| **Rule Loading Errors** | `rule_finder()` closure | Recoverable, returned to Backend | Invalid YAML syntax |
| **Request Handling Errors** | Backend methods | Recoverable, reported to IDE | Parse error in document |

**Error Context Wrapping:**

At [crates/cli/src/lsp.rs35](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lsp.rs#L35-L35) the initialization error is wrapped with context:

```rust
.map_err(|e| ErrorContext::StartLanguageServer.context(e))?;
```

`ErrorContext::StartLanguageServer` provides a user-friendly error message when the tokio runtime fails to initialize.

## Comparison with CLI Execution

The LSP server and CLI tool share the same core architecture but differ in execution model and lifecycle:

| Aspect | CLI Tool | LSP Server |
| --- | --- | --- |
| **Lifecycle** | One-shot execution | Long-running server |
| **Rule Loading** | Immediate on startup | Lazy via closure |
| **Output** | stdout with formatters | JSON-RPC over stdio |
| **Project Config** | Required for scan, optional for run | Always required |
| **Async Model** | Optional (threading) | Required (tokio) |
| **Error Handling** | Exit with error code | Return error to IDE |
| **Rule Reloading** | Not applicable | Future extension point |

Both paths use the same underlying components:

-   `ProjectConfig` for configuration discovery
-   `RuleCollection` for rule storage
-   `ast-grep-core` for pattern matching
-   `SgLang` for language support
