This page provides setup instructions for integrating the ast-grep Language Server Protocol (LSP) backend with various code editors. The LSP integration provides real-time diagnostics, code actions (quick fixes), and hover information based on your configured rules.

For the LSP architecture and implementation details, see [LSP Architecture](/ast-grep/ast-grep/6.1-lsp-architecture). For rule configuration, see [Rule System](/ast-grep/ast-grep/3-rule-system). For command-line usage, see [CLI Tool](/ast-grep/ast-grep/5-cli-tool).

## Prerequisites

Before setting up editor integration, ensure:

1.  **ast-grep is installed:** The `sg` or `ast-grep` binary must be in your `PATH`
2.  **Project configuration exists:** Your project must have an `sgconfig.yml` or `sgconfig.yaml` file
3.  **Rules are configured:** At least one rule directory specified in `ruleDirs` field

The LSP server is invoked via the `sg lsp` command and communicates over stdin/stdout using the standard JSON-RPC protocol.

**Minimal sgconfig.yml:**

```yaml
ruleDirs:
  - rules
```

The LSP server searches for configuration files starting from the current directory and walking up parent directories until it finds `sgconfig.yml` or `sgconfig.yaml`.

Sources: [crates/cli/src/lsp.rs10-37](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lsp.rs#L10-L37) [crates/cli/Cargo.toml1-66](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/Cargo.toml#L1-L66)

## LSP Server Command

The LSP server is started using:

```bash
sg lsp
# or
ast-grep lsp
```

**Command characteristics:**

| Property | Value |
| --- | --- |
| Communication | stdin/stdout |
| Protocol | JSON-RPC 2.0 (Language Server Protocol) |
| Root detection | Looks for `sgconfig.yml` or `sgconfig.yaml` |
| Supported file types | Determined by rules' `language` field |

The server runs until the client terminates the connection or sends a `shutdown` request.

Sources: [crates/cli/src/lsp.rs1-50](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lsp.rs#L1-L50) [crates/lsp/Cargo.toml1-40](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/lsp/Cargo.toml#L1-L40)

## VS Code

Install the official ast-grep extension from the VS Code marketplace. The extension automatically starts the LSP server when opening a workspace containing `sgconfig.yml`.

**Extension Settings (`.vscode/settings.json`):**

```json
{
  "ast-grep.path": "sg",
  "ast-grep.config": "./sgconfig.yml",
  "ast-grep.trace.server": "off"
}
```

**Available Settings:**

| Setting | Description | Default |
| --- | --- | --- |
| `ast-grep.path` | Path to sg binary | `"sg"` (from PATH) |
| `ast-grep.config` | Path to configuration file | Auto-detected |
| `ast-grep.trace.server` | LSP trace logging level | `"off"` |

The extension provides:

-   Real-time diagnostics as you type
-   Code actions (quick fixes) for rules with `fix` field
-   Hover information showing rule details
-   Support for `expandStart`/`expandEnd` in fixes

## Neovim

Neovim supports ast-grep LSP through various LSP client plugins.

### Using nvim-lspconfig

```lua
local lspconfig = require('lspconfig')

lspconfig.ast_grep.setup {
  cmd = { "sg", "lsp" },
  filetypes = { "javascript", "typescript", "python", "rust", "go" },
  root_dir = lspconfig.util.root_pattern("sgconfig.yml", "sgconfig.yaml", ".git"),
}
```

**Advanced Configuration:**

```lua
lspconfig.ast_grep.setup {
  cmd = { "sg", "lsp" },
  filetypes = { "javascript", "typescript" },
  root_dir = lspconfig.util.root_pattern("sgconfig.yml"),
  on_attach = function(client, bufnr)
    -- Custom keybindings for code actions
    vim.keymap.set('n', '<leader>ca', vim.lsp.buf.code_action, { buffer = bufnr })
  end,
}
```

### Using coc.nvim

**Configuration (coc-settings.json):**

```json
{
  "languageserver": {
    "ast-grep": {
      "command": "sg",
      "args": ["lsp"],
      "filetypes": ["javascript", "typescript", "python"],
      "rootPatterns": ["sgconfig.yml", "sgconfig.yaml"]
    }
  }
}
```

## Emacs

Configure ast-grep using `lsp-mode` or `eglot`.

### Using lsp-mode

**Configuration (init.el or .emacs):**

```elisp
(lsp-register-client
 (make-lsp-client
  :new-connection (lsp-stdio-connection '("sg" "lsp"))
  :major-modes '(js-mode typescript-mode python-mode rust-mode)
  :server-id 'ast-grep))

(add-hook 'js-mode-hook #'lsp)
(add-hook 'typescript-mode-hook #'lsp)
```

### Using eglot

**Configuration:**

```elisp
(add-to-list 'eglot-server-programs
             '((js-mode typescript-mode python-mode) . ("sg" "lsp")))
```

## Helix

Helix has built-in LSP support. Configure in `~/.config/helix/languages.toml`:

```toml
[language-server.ast-grep]
command = "sg"
args = ["lsp"]

[[language]]
name = "javascript"
language-servers = ["ast-grep", "typescript-language-server"]

[[language]]
name = "typescript"
language-servers = ["ast-grep", "typescript-language-server"]
```

This configuration adds ast-grep as an additional language server alongside existing ones.

## Generic Editor Configuration

For editors not listed above, configure the LSP client with these parameters:

| Parameter | Value | Notes |
| --- | --- | --- |
| Command | `sg lsp` or `ast-grep lsp` | Must be in PATH or use absolute path |
| Arguments | None | Command takes no additional arguments |
| Transport | stdio | Standard input/output |
| Root directory | Directory containing `sgconfig.yml` or `sgconfig.yaml` | Required for server to start |
| Workspace folders | Supported | LSP checks client capability first |
| File types | Language-specific | Match languages in your rules |
| Single file support | No | Requires project configuration |

## Features Provided by LSP

The ast-grep LSP server provides these standard LSP features:

**Diagnostics:**

-   Real-time linting based on configured rules
-   Severity levels: error, warning, info, hint (from rule's `severity` field)
-   Diagnostics include rule ID and message
-   Source identifier: "ast-grep"

**Code Actions (Quick Fixes):**

-   Available when rules include a `fix` field
-   Support for `transform` in fixes
-   Support for `expandStart`/`expandEnd` range extension
-   Multi-line fixes are disallowed to prevent conflicts

**Hover Information:**

-   Shows rule details when hovering over diagnostics
-   Includes rule message and optional note field

**Note:** The LSP server checks client capabilities during initialization and adapts its behavior. For example, it only sends workspace folder requests if the client advertises support for them.

Sources: [CHANGELOG.md75-78](https://github.com/ast-grep/ast-grep/blob/3ae01aec/CHANGELOG.md#L75-L78) [CHANGELOG.md92-96](https://github.com/ast-grep/ast-grep/blob/3ae01aec/CHANGELOG.md#L92-L96)

## Rule Reloading

The LSP server supports dynamic rule reloading when rule files change, allowing developers to test rule modifications without restarting the editor.

**Rule Reloading Implementation:**

```rust
let rule_finder = move || {
    project.find_rules(&RuleOverwrite::default())
};
```

The `rule_finder` closure pattern decouples rule loading from the LSP Backend, making it easy to reload rules by calling the closure again. This was implemented to support live rule development workflows.

## Implementation Details

### Rule Finding Mechanism

The `rule_finder` closure provided to the Backend implements the same rule loading logic as the CLI, ensuring consistency between editor and command-line behavior.

**Rule Loading Process:**

1.  **Utility Rules:** Load from `util_dirs` first to populate `GlobalRules`
2.  **Main Rules:** Load from `rule_dirs` with reference to `GlobalRules`
3.  **Validation:** Check glob patterns, variable references, and rule structure
4.  **Compilation:** Create efficient `CombinedScan` for multi-rule matching

Sources: [crates/cli/src/config.rs85-91](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/config.rs#L85-L91) [crates/cli/src/config.rs133-162](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/config.rs#L133-L162) [crates/cli/src/config.rs164-206](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/config.rs#L164-L206)

### Async Request Handling

The LSP implementation uses `tower-lsp-server` (version 0.23.0) for async request handling. The server processes LSP requests asynchronously while maintaining thread-safe access to shared state through `DashMap`.

**Threading Model:**

-   **Main Thread:** Tokio multi-threaded runtime handles IO and request routing
-   **Shared State:** `DashMap` (from `dashmap` crate) provides concurrent access to rule collections and diagnostics without explicit locking
-   **Rule Operations:** Pattern matching and AST operations are CPU-bound and run synchronously within async tasks

Sources: [crates/lsp/Cargo.toml26-27](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/lsp/Cargo.toml#L26-L27) [crates/cli/src/lsp.rs32-36](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lsp.rs#L32-L36)

### Error Handling

The LSP server uses structured error contexts defined in the CLI's `ErrorContext` enum:

```rust
pub enum ErrorContext {
    StartLanguageServer,
    ProjectNotExist,
    // ...
}
```

When the LSP encounters errors:

1.  **Startup Errors:** Fatal errors (missing config, invalid config) prevent server start and are reported to stderr
2.  **Request Errors:** Non-fatal errors (rule parsing failures) are logged but don't crash the server
3.  **Client Communication:** Errors during LSP request handling return standard LSP error responses

Sources: [crates/cli/src/lsp.rs31-37](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/lsp.rs#L31-L37) [crates/cli/src/config.rs70-83](https://github.com/ast-grep/ast-grep/blob/3ae01aec/crates/cli/src/config.rs#L70-L83)

## Configuration Best Practices

### Project Structure

Organize your project for optimal LSP performance:

```
my-project/
├── sgconfig.yml          # Root configuration
├── rules/               # Main rules directory
│   ├── typescript/
│   │   ├── no-console.yml
│   │   └── require-await.yml
│   └── rust/
│       └── no-unwrap.yml
├── utils/               # Global utilities (optional)
│   └── common.yml
└── src/                # Source code
    └── ...
```

### sgconfig.yml for LSP

Minimal configuration for LSP:

```yaml
ruleDirs:
  - rules
# Optional: utility rules
utilDirs:
  - utils
```

### Performance Considerations

-   **Rule Count:** The LSP scans files with all rules on every change. Keep rule collections focused.
-   **Glob Patterns:** Use `files` and `ignores` fields in rules to limit which files each rule applies to.
-   **Utility Rules:** Share common patterns through `utils` to reduce duplication and improve maintainability.
